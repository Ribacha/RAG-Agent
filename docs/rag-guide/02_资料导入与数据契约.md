# 资料导入与数据契约

RAG 的第一步不是调用聊天模型，而是把不规则的文件转换成稳定、可追踪的数据。导入层决定后面的系统能不能找到正确内容、能不能告诉用户来源、能不能在文件变化后安全更新。

## 1. 输入边界

当前项目接受：

```text
.pdf
.md / .markdown
.txt
```

CLI 可以接收单个文件或目录：

```bash
python -m rag_agent ingest "/path/to/a.pdf"
python -m rag_agent ingest "/path/to/docs"
```

目录导入会递归搜索受支持的扩展名，跳过隐藏目录、符号链接和临时文件。这样做是一个安全边界：用户明确选择的目录不应该因为符号链接而越界读取其他路径。

## 2. 导入的实际产物

默认目录下会产生：

```text
data/index/chunks.jsonl       # 分块正文和来源元数据
data/index/documents.jsonl    # 每个文件一行的摘要清单
data/index/vectors.jsonl      # 向量索引
data/failed/ingestion.jsonl   # 失败文件和错误原因
```

这四个文件的职责不同：

- `documents.jsonl` 用来知道哪些文件成功、使用了什么解析方法、有哪些 warning。
- `chunks.jsonl` 是可读的中间结果，最适合学习和排查分块问题。
- `vectors.jsonl` 给检索器使用，包含索引 meta、向量和对应 Chunk。
- `ingestion.jsonl` 让批量导入中的单文件失败可追踪，不遮蔽其他成功文件。

## 3. 文件 -> DocumentRecord

`src/rag_agent/ingest/pipeline.py` 负责发现文件和选择加载器。加载器输出 `DocumentRecord`，它代表一个文件版本，包含：

```text
doc_id
source_id
source_path
file_type
content_hash
size_bytes
blocks: list[TextBlock]
warnings
ingestion_fingerprint
```

### `source_id` 和 `doc_id`

`source_id` 根据规范化后的绝对路径计算，表示“这是哪个来源”。

`doc_id` 根据 `source_id + content_hash` 计算，表示“这个来源的哪一个内容版本”。

因此，同一个文件内容被修改后会得到新的 `doc_id`；文件路径和文件内容分别有清晰的身份，不会因为简单改名或内容变化而悄悄复用旧版本。

### 为什么保存 `content_hash`

增量导入不应该每次都重新解析和重新计算所有向量。通过内容哈希，可以判断文件字节是否变化；再结合解析和分块配置指纹，才能决定旧结果是否可以复用。

## 4. DocumentRecord -> TextBlock

`TextBlock` 是解析器输出的最小单元：

```text
doc_id
source_path
file_type
text
extraction_method
page_number
heading_path
warnings
encoding
```

不同格式有不同的自然单元：

| 格式 | TextBlock 通常代表 |
| --- | --- |
| TXT | 规范化后的文本段落 |
| Markdown | 带标题路径的段落或代码块 |
| PDF | 一页文本，保留页码 |

统一成 `TextBlock` 后，分块器不需要知道 PDF 或 Markdown 的解析细节。

## 5. 文本文件的规范化

`src/rag_agent/ingest/text.py` 会处理常见编码和换行差异，包括 UTF-8、UTF-16、GB18030 等候选编码，并把 CRLF 统一为 LF。

这一步的目标不是“修复所有乱码”，而是让同一份逻辑文本尽可能得到稳定的内容和偏移。编码会被记录到 manifest，出现异常时可以定位。

## 6. Markdown 的额外价值

Markdown 的标题不是装饰，它是检索证据的重要上下文。例如：

```markdown
# TCP
## 三次握手
客户端首先发送 SYN。
```

检索结果应该保留类似：

```text
heading_path = ['TCP', '三次握手']
```

这样用户看到引用时，不只知道文件名，还知道证据位于哪一节。

## 7. PDF 和 OCR

`src/rag_agent/ingest/pdf.py` 使用 PyMuPDF 逐页读取文本块，按版面顺序拼接。页面原生文本太短、为空或包含过多替换字符时，认为可能是扫描页：

```text
原生文本质量不足
  -> --ocr 开启时调用 Tesseract
  -> OCR 成功则 extraction_method=pdf_ocr
  -> OCR 不可用则保留 warning，不伪造空文本
```

导入扫描 PDF：

```bash
python -m rag_agent ingest data/inbox \
  --ocr --ocr-language 'chi_sim+eng'
```

这不是版面理解系统。当前实现按页提取，复杂双栏、表格和图片中的结构仍可能需要后续增强，必须通过检索测试验证，而不能只看“导入成功”。

## 8. 失败处理原则

批量导入时，一个坏 PDF 不应该让所有 TXT 都消失。项目把每个文件的异常转换成 `FailedDocument`，继续处理其他文件，并用退出码 2 告知调用方存在失败。

这带来三个实际好处：

1. 成功结果可以立即被检索。
2. 失败文件有明确路径、类型和原因。
3. 自动化任务可以根据退出码决定是否报警。

## 9. 先检查中间结果再接模型

学习时建议先运行：

```bash
python -m rag_agent ingest data/inbox
python -m rag_agent list-documents --json
head -3 data/index/chunks.jsonl
```

重点检查：

- 文本是否完整，是否出现乱码。
- PDF 页码和 Markdown 标题是否存在。
- Chunk 数量是否合理。
- warning 是否反映真实问题。
- `source_path` 是否是你期望的路径。

如果这里的文本就错了，后面换 Embedding 或模型都不能补救。
