# 分块与元数据设计

Embedding 和检索处理的不是“整本书”，而是一组 Chunk。Chunk 怎么切，直接决定检索到的证据是否足够完整、是否包含必要上下文、是否能准确引用原文。

## 1. 为什么不能把整份文件做成一个向量

整份文件只有一个向量会造成两个问题：

- 一个问题只能命中整份文件，粒度太粗，无法控制上下文长度。
- 一个文件内容很多时，相关段落被不相关内容稀释，模型收到的证据不够聚焦。

如果切得过细，也会出现相反问题：定义在上一块，解释在下一块，单独检索任一块都不完整。

分块的目标是让一个 Chunk 尽可能成为“可以独立支持一个小结论的证据单元”。

## 2. 当前项目的分块算法

实现位于 `src/rag_agent/chunking/splitter.py`，配置对象是：

```python
ChunkConfig(
    max_chars=1200,
    overlap_chars=120,
)
```

处理过程：

1. 去除首尾空白，同时保留相对偏移。
2. 以字符数限制块大小。
3. 在达到硬上限前，优先寻找自然边界。
4. 自然边界包括换行、中文句号、问号、感叹号、分号和空格。
5. 下一块从上一块末尾回退 `overlap_chars`，保留少量上下文。
6. 输出半开区间 `[start, end)`，便于追踪原文位置。

## 3. `max_chars` 和 `overlap_chars` 怎么理解

假设：

```text
max_chars = 1000
overlap_chars = 100
```

一个长文本可能被切成：

```text
Chunk 1: [0, 1000)
Chunk 2: [900, 1900)
Chunk 3: [1800, 2800)
```

重叠不是越大越好：

- 重叠太小，跨边界的定义和上下文可能断裂。
- 重叠太大，重复内容增加，索引膨胀，Top-K 可能被相邻重复块占满。

当前项目在字符级工作，没有绑定某一家 tokenizer。对于中文资料，这种方式易理解、可重复；生产系统可以进一步增加 token-aware 分块，但应保持 Chunk 数据契约不变。

## 4. 自然边界为什么重要

硬切字符串可能得到：

```text
...客户端首先发送 SYN，服务器收到后返回...
```

下一块才出现“这就是三次握手的第一步”。自然边界优先让语义单元尽量完整。

但自然边界不是语义理解器。很长的表格、代码、没有标点的 OCR 文本仍可能被硬切，所以需要在实际资料上检查结果。

## 5. Chunk 中保存哪些元数据

当前 `Chunk` 至少包含：

```text
chunk_id
doc_id
source_id
source_path
file_type
text
chunk_index
content_hash
page_start / page_end
heading_path
char_start / char_end
extraction_methods
warnings
ingestion_version
chunking_version
ingestion_fingerprint
chunking_fingerprint
```

这些字段不是多余信息：

| 字段 | 用途 |
| --- | --- |
| `chunk_id` | 稳定识别一个具体证据单元 |
| `source_path` | 输出引用、定位原始文件 |
| `page_start` | PDF 引用页码 |
| `heading_path` | Markdown 章节上下文 |
| `content_hash` | 判断正文是否变化 |
| offsets | 调试、回到原文位置 |
| warnings | 把 OCR/解析质量问题带到检索结果 |
| fingerprints | 防止错误复用旧处理结果 |

## 6. Chunk ID 为什么不能只用序号

如果只用 `chunk-17`，一旦前面插入一段文字，后面的序号都会改变，很难判断哪些块真正变化。

当前项目把来源身份、文档版本、块序号、文本哈希和处理指纹一起计算 SHA-256：

```text
chunk:v2 | source_id | doc_id | content_hash | chunk_index
         | ingestion_fingerprint | chunking_fingerprint
```

这样同一份输入和配置可以复现相同 ID；文件移动、内容变化或分块策略变化不会与旧块悄悄碰撞。

## 7. 不同资料类型的分块思路

### 教程和技术文档

优先保持标题和完整段落。定义、条件、例子最好在同一块或有足够 overlap。

### 问答资料

问题和答案不要分离。如果一问一答很短，可以让一组问答成为一个 Chunk；如果答案很长，再按段落切分并保留问题标题。

### 代码

尽量以函数、类或代码块为边界，避免把函数签名和主体分开。当前字符分块器只识别通用边界，复杂代码资料应通过专项测试决定是否需要专用 loader。

### PDF 表格

当前按页文本提取，表格列关系不一定保留。不能仅靠增大 Chunk 解决结构丢失；需要结构化表格提取器或在导入阶段转换为带列名的文本。

## 8. 如何调参

不要凭感觉一次改很多参数。建议固定一组问题，逐次比较：

```bash
python -m rag_agent ingest data/inbox \
  --max-chars 800 --overlap-chars 80

python -m rag_agent evaluate data/eval/retrieval.jsonl \
  --top-k 5 --json
```

记录每次配置、Chunk 数量、Recall@K 和典型失败样本。分块优化的目标不是 Chunk 越少或越多，而是“正确证据更容易以完整单元出现在 Top-K 中”。

## 9. 分块完成的验收标准

- 相邻 Chunk 有适度上下文，但不会大量重复。
- 重要定义不会系统性地被切成半句。
- 每个 Chunk 可以追溯到文件、页码或标题。
- 相同输入和配置重复运行时 ID 稳定。
- 资料变化后只影响应该变化的 Chunk。
- 评测集中的相关 Chunk 能进入目标 Top-K。
