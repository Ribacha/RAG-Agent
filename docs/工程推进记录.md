## 阶段 7 推进记录：增量导入基础版

本轮已完成阶段 7 中的增量导入基础版，代码位于
`src/rag_agent/ingest/incremental.py`，并接入 `ingest --incremental`。

行为契约：

- 输入为目录时，新增文件会导入，内容或解析/分块指纹变化的文件会重建，磁盘上已删除的来源会从快照和向量索引移除；输入为单文件时只更新该来源，不影响其他来源。
- 内容哈希、解析指纹、分块指纹和 chunk 数都未变化时，直接复用旧 chunks，不重复解析。
- 增量重建向量索引时，只对新增或变化的 chunk 调用 embedding；provider/model/dimension 变化时自动放弃复用并完整重建，避免混用向量。
- 单文件解析失败会写入失败清单，并保留该来源上一版可用 chunks；新增文件解析失败则不会产生半成品来源。
- JSONL 和向量文件仍使用原子替换，最终快照按来源和 chunk 顺序稳定写出。

命令示例：

```bash
PYTHONPATH=src python -m rag_agent ingest data/inbox --incremental
```

输出会额外包含 `documents_added`、`documents_updated`、`documents_unchanged`、
`documents_deleted`、`chunks_reused`、`chunks_generated`、`vectors_reused` 和
`vectors_embedded`，用于审计本次更新是否真的跳过了未变化内容。

本轮验收：38 个单元测试通过，覆盖 unchanged/update/delete、失败保留旧版本、
provider 变化时完整重建以及 CLI 端到端更新。当时阶段 7 的 LangGraph 状态图和评测集
尚未开始；后续记录已补齐 Recall@K/引用正确率评测格式。

## 阶段 7 推进记录：离线评测

本轮完成检索层离线评测，代码位于 `src/rag_agent/evaluation.py`，命令为
`rag-agent evaluate`。评测集采用 JSONL，每行一个样本：

```json
{"name":"attention","query":"Query、Key 和 Value 有什么关系？","relevant_chunk_ids":["chunk-attention"]}
{"query":"TCP 如何建立连接？","relevant_source_paths":["/docs/network.txt"]}
```

实现约束：

- `query` 必须是非空字符串；`relevant_chunk_ids`、`relevant_source_paths` 必须是字符串数组，且至少一个非空；空文件、空标注和错误类型都会带行号报错。
- 每条样本可用 `name` 或 `id` 标识，也可用 `min_score` 覆盖全局阈值；来源路径按索引中的 `source_path` 精确匹配。
- `Recall@K` 定义为 Top-K 是否命中任一相关 chunk/source 的样本比例；`citation_accuracy` 定义为每条查询返回结果中相关结果的比例，再对样本取平均。
- `citation_accuracy` 是 retrieval citation proxy，只衡量检索结果是否落在标注集合中，不代表聊天模型的事实正确率；评测不调用聊天模型，完全离线。
- 报告保留逐样本检索结果、实际阈值、命中的 chunk/source，支持审计和回归定位。

命令示例：

```bash
python -m rag_agent evaluate data/eval/retrieval.jsonl --top-k 5 --json
```

本轮验收：43 个单元测试通过（新增评测样本校验、chunk/source 标注命中、阈值覆盖、
指标聚合和 CLI JSON 输出），并通过 `compileall`。阶段 7 尚未完成的部分是对话历史
和 LangGraph 状态图，下一步先推进可观察的状态契约。

## 阶段 7 推进记录：对话历史与 Agent 状态

本轮完成 Agent 的有界对话历史和可序列化运行状态，代码位于
`src/rag_agent/agent/history.py` 与 `src/rag_agent/agent/runtime.py`，CLI 接入
`agent --history`、`--save-history` 和 `--history-max-turns`。

行为契约：

- 历史文件是一个 JSONL 快照对象，包含 `schema_version`、`max_turns` 和 `turns`；每轮只保存非空的 `user` 与 `assistant` 字段，默认最多 20 轮，允许范围为 1 到 100 轮。
- `KnowledgeAgent.run(question, history=...)` 会把历史转换为 user/assistant 消息并放在当前问题之前；旧历史不会被当作 system 消息，当前运行的 tool-call/tool-result 不写入历史，避免产生悬空协议链。
- 正常完成的回答会追加到返回值 `AgentResult.history`，可原子写回文件；达到 `max_steps` 的停止结果只保留在 `AgentState` 审计快照中，不追加到后续上下文。
- `AgentState` 包含本轮完整消息、工具调用审计、证据、执行步数、答案、停止原因和更新后的历史，`AgentResult.to_dict()` 可直接输出 JSON，便于后续迁移到 LangGraph 节点状态。
- 历史文件版本、轮次字段、空文本、最大轮数和多对象 JSONL 都会严格校验；不存在的 `--history` 文件按空历史开始，损坏文件直接报错。

命令示例：

```bash
python -m rag_agent agent "第一个问题" --history data/state/conversation.jsonl
python -m rag_agent agent "基于刚才的回答继续解释" --history data/state/conversation.jsonl --json
```

本轮验收：48 个单元测试通过（新增历史裁剪、JSONL 往返、格式校验、跨轮消息顺序、
中止不落历史和 CLI 持久化测试），并通过 `compileall`。阶段 7 尚未完成的部分是
更强的中文 embedding 和 LangGraph 状态图；下一步先评估 embedding 替换方案，再进入
可选依赖的图编排。

## 阶段 7 推进记录：中文离线增强 embedding

本轮增加 `src/rag_agent/embeddings/chinese.py`，实现无需网络和额外依赖的中文字符
n-gram embedding，并接入 `create_embedding_provider`、导入、搜索、问答、Agent 和
增量索引路径。provider 名称为 `chinese`，模型标识为 `chinese-ngram-v1`。

实现约束：

- 中文连续文本生成 1-4 字符重叠 n-gram；英文和数字保留 token 及短 n-gram；输入统一做 NFKC 和大小写归一化，降低全角标点和大小写差异影响。
- 向量仍使用确定性有符号特征哈希和 L2 归一化，输出维度默认 512，最小 64；因此完全离线、可复现、可审计，但不宣称具备训练语义模型的能力。
- provider 指纹包含 `chinese-ngram-v1` 和维度。现有索引兼容检查和增量复用逻辑会阻止 `hash`/`chinese` 混用，切换 provider 必须重建索引。
- 默认 provider 仍是 `hash`，避免已有索引和脚本无提示改变；只有显式 `--embedding-provider chinese` 或 `EMBEDDING_PROVIDER=chinese` 才启用增强基线。

命令示例：

```bash
python -m rag_agent ingest data/inbox --embedding-provider chinese
python -m rag_agent search "三次握手如何建立连接" --embedding-provider chinese
```

本轮验收：53 个单元测试通过（新增 provider 确定性、中文短语检索、工厂别名、
维度校验、provider 隔离和 CLI 端到端测试），并通过 `compileall`。下一条记录完成
LangGraph 状态图后，阶段 7 即收口。

## 阶段 7 推进记录：LangGraph 状态图

本轮完成可选 LangGraph 编排层，代码位于 `src/rag_agent/agent/graph.py`，CLI 通过
`agent --graph` 启用。默认手写 `KnowledgeAgent` 循环继续保留，未安装 LangGraph 时
不会影响导入、检索、离线评测或普通 Agent。

状态契约：

- `GraphState` 使用普通字典字段保存 `question`、`messages`、`pending_tool_calls`、`tool_calls`、`evidence`、`step`、`answer`、`stopped_reason` 和 JSON 形式的 `history`，可直接交给 LangGraph 检查点或输出审计。
- `agent` 节点调用现有 `ToolCallingChatProvider`；有工具调用时进入 `tools`，没有工具调用时进入 `finalize`。
- `tools` 节点复用 `KnowledgeSearchTool.invoke_json` 的参数校验和只读边界，记录每个调用的 step、参数、结果和证据；达到 `max_steps` 后进入 `finalize`。
- `finalize` 只把 `completed` 回答追加到 `ConversationHistory`，中止运行只保留在 `AgentState`，与手写循环的历史语义一致。
- `run_knowledge_graph` 将最终图状态转换回现有 `AgentResult`/`AgentState`，因此 CLI JSON、历史文件和下游调用不需要分叉数据格式。
- LangGraph 只在 `build_knowledge_graph` 时惰性导入；缺少依赖会抛出带安装命令的 `GraphUnavailableError`，而不是在导入 `rag_agent` 时让基础功能失效。

命令示例：

```bash
python -m pip install -e ".[graph]"
python -m rag_agent agent "Transformer 的注意力如何计算" --graph --json
```

本机当前未安装 LangGraph，因此没有进行真实第三方包运行；已通过纯离线节点测试、
模拟 `StateGraph` 构建测试、依赖惰性检测和完整回归测试。新增测试覆盖模型节点、工具
节点、收口节点、条件路由、max-step 不落历史和构建器节点注册。阶段 7 至此完成，下一步
进入阶段 8 的 OCR/版面增强前先暂停。

## 阶段 8 推进记录：真实 CLI RAG 闭环验证

本轮没有引入 Web UI，先用临时知识库验证最终用户实际会运行的 CLI 链路。临时知识库
包含项目 README 和本规划文档两份 Markdown，使用内置 `chinese` embedding，执行了：

```text
ingest -> search -> evaluate -> ask --dry-run
```

实跑结果：

- `ingest` 成功处理 2 个文档，生成 162 个 chunk，失败数为 0；向量索引的 provider
  指纹为 `chinese:chinese-ngram-v1:d128`。
- `search "报告包含 Recall@K 和 citation_accuracy"` 将工程规划中的“阶段 7 推进记录：
  离线评测”段落排在第 1 位，结果包含真实 `source_path`、标题路径和 `chunk_id`。
- 两条 JSONL 标注通过 `evaluate --top-k 5 --min-score 0.08`，报告为
  `Recall@5=1.0`、`citation_accuracy=0.4`。后者只是检索层引用正确率代理，不能替代
  聊天模型事实性评测。
- `ask --dry-run` 将同一段落作为编号 `[1]` 证据放入上下文，并保留来源元数据；对陌生
  问题使用 `--min-score 0.5` 时返回“知识库中没有找到足够相关的内容”，不调用聊天 API。
- 新增 `tests/integration/test_cli_rag.py`，用临时目录自动重复上述四个命令，并断言来源
  命中、`Recall@K`、证据上下文和无证据分支；当前完整回归为 59 个测试通过。

这次验证证明了“文件 -> 抽取 -> 分块 -> embedding -> 索引 -> Top-K -> RAG 证据上下文”
是真实可运行的离线闭环，而不只是单元测试。当前环境没有 `LLM_API_KEY`，因此外部聊天
模型的网络调用和生成质量仍需用户提供有效 Key 后单独验证；不能把 dry-run 结果称为模型
生成成功。下载后的 CLI 验证也已完成；下一步继续阶段 8 的 PDF 双栏/表格/OCR 质量与
权限边界增强。
